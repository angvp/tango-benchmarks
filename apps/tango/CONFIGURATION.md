# tanGO pet shop: configuration

Built from `tango newproject petshop` of **tanGO v0.4.0** (the released tag, installed with `go install github.com/angvp/tango/cmd/tango@v0.4.0`), then the pet shop added by hand in `apps/shop`. Documented defaults throughout; nothing tuned.

| Setting | Value |
|---|---|
| Framework | `github.com/angvp/tango v0.4.0` |
| Go | the toolchain in the build image (`golang:1.27-alpine`), `CGO_ENABLED=0` |
| Database driver | pgx stdlib, through tanGO's `db.Store` (PostgreSQL 17) |
| Server | `tango.ServeContext` (graceful shutdown, 10 s header timeout), listening on `TANGO_ADDR=:8080` |
| Middleware | the scaffold's defaults: `RequestID`, `Recoverer`, `AccessLogger`, `MaxBodySize(1 MiB)`, `MiddlewareScopeAll` |
| API auth | `auth/jwt` bearer tokens issued by `POST /api/login` after checking the admin account's bcrypt hash |
| Admin | tanGO's built-in admin, installed after the app that registers models with it, as documented |
| Staff account | created at container start with `-tango-admin-create=bench-staff` and `TANGO_ADMIN_PASSWORD` (a benchmark credential) |
| Migrations | generated by `tango makemigrations`, applied at container start with `-migrate` |
| Process | one process, no worker setting (tanGO has none) |
| Container limits | 2 CPUs, 2 GiB, the same as every other app |

Access logging is on, as the scaffold ships it: it costs something under load and is part of the framework's default behaviour, so it stays on.
