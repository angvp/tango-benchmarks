# Django pet shop: configuration

Built from `django-admin startproject petshop` and `manage.py startapp shop` of **Django 6.1.2** (the current stable release), then the pet shop added by hand. Django itself only: no Django REST framework, no Ninja, no extra packages beyond the server and the database driver. Those are common additions for an API and a reasonable variant for a later run; the core framework has no API layer, so the JSON views are written by hand.

| Setting | Value |
|---|---|
| Framework | `Django==6.1.2` |
| Python | 3.13 (`python:3.13-slim`) |
| Database driver | `psycopg[binary]==3.3.6` (PostgreSQL 17) |
| Server | `gunicorn==26.2.0`, sync workers, `--workers 2` (the container's CPU limit) |
| Settings | `DEBUG = False`, `ALLOWED_HOSTS = ['*']`, secret key from `DJANGO_SECRET_KEY` (a throwaway default) |
| Persistent connections | `CONN_MAX_AGE = 60`. Django's default is 0 (a new connection for every request); the deployment guidance recommends reusing connections, so this is the production setting. Revisit with 0 if the numbers look surprising. |
| API auth | `django.core.signing` signed tokens, 12 hour lifetime, issued after `django.contrib.auth.authenticate` |
| CSRF | the middleware stays on; the JSON views are `csrf_exempt` because they authenticate with a bearer token, not a cookie |
| Admin | `django.contrib.admin`; its CSS and JavaScript are not served (a production Django serves static files from a web server or WhiteNoise, which is outside the framework); the HTML pages themselves are served in full |
| Staff account | `createsuperuser --noinput` at container start with a throwaway password |
| Migrations | generated by `makemigrations` and applied with `migrate` at container start |
| Container limits | 2 CPUs, 2 GiB, the same as every other app |
